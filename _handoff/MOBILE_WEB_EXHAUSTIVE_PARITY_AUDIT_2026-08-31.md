# تدقيق التطابق الشامل بين ويب الهاتف وتطبيق الهاتف

التاريخ: 2026-08-31
الحالة: تدقيق شامل مكتمل للشفرة، المسارات، الواجهات، الـ API وقاعدة البيانات وAndroid Release؛ فحص iOS Runtime متوقف على توقيع Apple.

## الحكم التنفيذي

التطبيق **Native حقيقي مبني بـ React Native/Expo** ويستهلك خدمات المشروع وقاعدة Supabase نفسها، وليس WebView. لكن النتيجة الحالية **ليست 1:1 بصرياً أو عملياً** مع نسخة الويب على الهاتف. تطابق مصدر البيانات والمسارات الأساسية جيد، بينما توجد فروقات جوهرية في هيكل التنقل، البحث والفلترة، تفاصيل المنتج، الدفع، الاستبدال، المصادقة، الوصول، وبعض حالات الخطأ.

لا يصح اعتبار اختبارات وجود المسارات القديمة دليلاً على 1:1؛ فهي تثبت وجود ملفات وعقود أساسية فقط. هذا التقرير يلغي أي تفسير سابق يوحي بأن 91 اختباراً تعني تطابقاً بصرياً ووظيفياً كاملاً.

## نطاق الفحص والأدلة

- 27 مساراً وظيفياً متقابلاً بين الويب والتطبيق، مع مسارات مصادقة إضافية على الويب ومسار onboarding إضافي في التطبيق.
- 198 حالة ويب فعلية: 33 واجهة/حالة × العربية والإنجليزية × `360x800` و`390x844` و`412x915`.
- 198 لقطة ويب بعد إضافة مجموعة حقيقية `quiet-luxury`؛ جميع حالات المجموعة الست أعادت 200، بلا صور مكسورة أو انزلاق أفقي، وباتجاه RTL/LTR الصحيح.
- تحليل شفرة Native لكل الشاشات والعمليات، وربط كل عملية بمصدر البيانات أو API المقابل.
- لقطات Android فعلية للرئيسية والتصنيفات وعدة حالات أخرى من تشغيل SDK 54.
- مقارنة بكسلية ممثلة بعد توحيد القياس:
  - الرئيسية: 2.814% فقط من البكسلات متطابقة تماماً؛ 54.88% ضمن فرق 10/255 في القنوات؛ متوسط الفرق 28.24.
  - التصنيفات: 19.888% متطابق تماماً (معظمها مساحات الخلفية)؛ 51.19% ضمن فرق 10/255؛ متوسط الفرق 46.27.
  - هذه الأرقام تشمل فروق شريط النظام ومحرك الخط والرسم، لكنها تثبت قطعاً أن النتيجة ليست pixel-perfect.
- اكتُشف أن الملف القديم المسمى `android-offers-final3.png` يعرض شاشة الحساب، لا شاشة العروض؛ لذلك تم استبعاده من أدلة مطابقة العروض.
- اختبارات المشروع: 91/91 ناجحة.
- TypeScript: 9/9 مساحات عمل ناجحة.
- اختبار حي للعميل وقاعدة البيانات: 14/14 ناجح، مع تنظيف المستخدم والطلب والعنوان المؤقتة.
- Expo Doctor: 18/18 بعد إصلاح دمج `watchFolders` الافتراضية في Metro.
- Android EAS 1.0.2/versionCode 3: بناء ناجح، تنزيل وتثبيت ناجحان على المحاكي، و18 deep link بلا crash.
- بدء Android البارد: 1970ms على المحاكي.
- تبديل العربية RTL إلى الإنجليزية LTR مثبت فعلياً من APK.
- نشر الإنتاج الحالي لا يضم كل APIs الجديدة: `/api/storefront/home` و`/api/categories` يعيدان 404، بينما `/api/products` و`/api/settings/exchange-rate` يعملان. لذلك الرئيسية والتصنيفات والمجموعات لا تعمل في APK المنشور حالياً.

## المقارنة التفصيلية

### الهيكل العام والتنقل

- الويب يضع Header وFooter وMobileBottomNav على جميع صفحات `(main)`.
- Native يعرض Bottom Tabs داخل مجموعة `(tabs)` فقط؛ صفحات المنتج، الدفع، الطلبات، الحساب، الاستبدال، القانون وغيرها تفقد شريط التنقل السفلي.
- Header الويب عالمي؛ Native يستخدم `AppTopBar` في الرئيسية والتصنيفات، Header مختلف في الكتالوج، و`ScreenHeader` في الصفحات الداخلية.
- Footer الويب غير موجود كتجربة عالمية في Native؛ بعض روابط الدعم موزعة داخل الحساب فقط.
- الروابط المحمية في BottomNav الويب تفتح Auth modal، بينما Native ينتقل إلى شاشة ضيف فيها CTA للدخول.
- النتيجة: بنية التنقل ليست 1:1 حتى عندما يكون محتوى الصفحة متشابهاً.

### الرئيسية

- مصدر البيانات وترتيب hero/brands/categories/product themes/new/VIP متقارب ويعتمد `/api/storefront/home` في Native.
- ضغطة العلامة التجارية في الويب تحمل `brands=slug`؛ Native يفتح `/products` بلا فلتر العلامة.
- SmartSearch الويب يكتب ويقترح منتجات وتصنيفات ويوجه مباشرة؛ زر البحث في AppTopBar Native يفتح صفحة المنتجات فقط بلا استعلام أو اقتراحات.
- صورة hero والنص والزر قريبون بصرياً، لكن القياسات والخطوط وارتفاع الصورة وشريط النظام والـ spacing ليست بكسل ببكسل.

### الكتالوج والتصنيفات والعروض والجديد والمجموعات

- كلاهما يدعم بحثاً وفرزاً وتصنيفات وعلامات وخصائص وسعر minimum/maximum.
- الويب يضيف `sale` و`featured-only` داخل واجهة الفلاتر؛ Native لا يعرضهما كخياري فلترة عامين.
- الويب يحفظ q/categories/brands/attrs/minPrice/maxPrice في URL. Native لا يهيئ كل هذه القيم من deep link ولا يعكس تغييرات المستخدم في URL.
- الويب يعرض 24 منتجاً وصفحات Previous/Next؛ Native يعرض 20 ثم Load more.
- بطاقات المنتج مختلفة في ترتيب badges، المخزون، خيارات المتغير، وحضور زر المفضلة. بعض بطاقات الويب تخفي المفضلة بـ hover، وهو سلوك غير ملائم للمس.
- صفحة المجموعة على الويب تستخدم ISR لمدة 60 ثانية؛ Native يطلب API حي، لذلك قد يظهر اختلاف زمني يصل إلى دورة إعادة التحقق.

### تفاصيل المنتج

- مصدر المنتج والصور والفيديو والمتغيرات والمقاسات والباقات والمراجعات وNotify-me والمشاركة وإضافة السلة موجود في الطرفين.
- Native يفتقد المفضلة في صفحة التفاصيل، المنتجات المشابهة، وRecently Viewed الموجودين في الويب.
- خوارزمية المتغير مختلفة: الويب يحتفظ باختيارات متعددة ويحسب التوافق الدقيق ويعطل التركيبات غير المتاحة؛ Native قد يستبدل الاختيارات بمتغير يحتوي الخاصية المضغوطة فقط، ولا يعطل كل التركيبات غير المتوافقة بالطريقة نفسها.
- Native يضيف quantity/total قبل الإضافة؛ الويب يضيف واحدة مباشرة. هذا اختلاف وظيفي لا مجرد اختلاف تصميم.

### السلة

- القراءة/الكتابة والمزامنة والكمية والحذف والإجمالي والانتقال للدفع موجودة.
- الويب يعرض SKU وbundle label وإجمالي السطر وعدد القطع وزر متابعة التسوق ورسائل تأكيد؛ Native لا يعرض كل هذه التفاصيل.
- CTA السلة الفارغة يذهب للتصنيفات في Native وللمنتجات في الويب.

### الدفع

- الطرفان ينشئان الطلب عبر `/api/orders` مع idempotency وCOD والشحن والخصومات والولاء.
- الويب يتحقق من الكوبون قبل الإرسال عبر `/api/cart/apply-discount` ويعرض قيمة الخصم وخطأ inline وإزالة الكوبون. Native يرسل النص عند إنشاء الطلب فقط، ويعرض الخطأ عبر Alert، ولا يحدّث التقدير قبل جواب الخادم.
- الويب يوفر ملاحظات الطلب؛ Native لا يوفرها.
- الويب يحفظ العنوان الجديد عبر `/api/addresses`؛ Native يرسل `address_snapshot` ولا يحفظ العنوان في دفتر المستخدم.
- الويب يعتمد سلة الخادم عند الطلب؛ Native يرسل items صراحةً إلى نفس endpoint. الخادم يدعم الاثنين، لكن العملية ليست متطابقة.
- مسار النجاح مختلف: الويب يذهب مباشرة لتفاصيل الطلب؛ Native يذهب لشاشة نجاح ثم قائمة الطلبات.

### الطلبات والفاتورة والمراجعات

- List/detail/cancel/reorder/invoice/exchange/review مدعومة إجمالاً وبنفس البيانات الأساسية.
- Native يسمح بالإلغاء من القائمة؛ الويب لا يعرضه في القائمة.
- Native يعرض subtotal/discount/loyalty/shipping؛ الويب يركز على total.
- عنوان المنتج رابط في الويب وليس رابطاً في Native.
- نموذج المراجعة ومكانه وتتبّع حالة الإرسال مختلفان.

### المفضلة والمشاركة

- `/api/wishlist` و`/share` وshared token مشتركة، مع Share sheet في Native ونسخ/مشاركة في الويب.
- سلوك الضيف والدمج بعد تسجيل الدخول مختلف في الواجهة، رغم تقارب مخزن البيانات.

### الولاء

- الرصيد وQR والإحالة والقواعد موجودة.
- Native يعرض آخر العمليات، وهي غير معروضة في الويب.
- الويب يوفر تنزيل QR ونسخ الإحالة وbonus/tip ورابط الطلبات؛ Native لا يوفر جميعها.
- حالة الضيف في Native قد تظهر كفشل تحميل عام؛ الويب يعرض دعوة دخول واضحة.

### الإشعارات

- list/read/read-all تستخدم endpoints نفسها.
- Native يجعل كامل الإشعار قابلاً للضغط لتحديده كمقروء؛ الويب يملك زر unread صريحاً.
- الويب يعرض error + retry؛ Native يخفي بعض أخطاء التحميل والتحديث أو يتراجع optimistically بلا رسالة.
- الويب يعيد الضيف إلى login؛ Native يعرض CTA داخل الشاشة.

### الاستبدال

- القائمة والإنشاء والتفاصيل والصور وQR تعتمد نفس عائلة endpoints والبيانات.
- الويب يعرض CTA طلب جديد والسياسة للضيف؛ Native قد يحول 401 إلى قائمة فارغة ولا يعرض CTA/policy بالشكل نفسه.
- إنشاء الويب يحمّل الطلبات المؤهلة ويسمح باختيار الطلب والقطعة. إنشاء Native يتطلب `orderId` و`itemId` مسبقين من تفاصيل الطلب؛ فتحه من القائمة أو الحساب وحده غير قابل للإكمال.
- Native يستخدم منتقي الصور؛ صلاحية الكاميرا معلنة لكن لا توجد واجهة تصوير مباشرة.
- تفاصيل الويب تعرض timeline، resolution path، partner stage، QR used/expired/loading، الموقع، تنزيل QR، وروابط الدعم. Native يعرض الحالة الحالية والسبب والرفض وQR الصالح والصور فقط.

### الحساب والعناوين

- تعديل الاسم والهاتف والجنس مربوط في الطرفين.
- Dashboard الويب يعرض الاسم والهاتف والإحالة ونقاط الولاء وعدد الطلبات والاستبدالات؛ tab الحساب Native لا يعرض الإحصاءات نفسها.
- Native يجمع اللغة والتفضيلات في الحساب؛ الويب يضع اللغة ضمن تنقل الحساب.
- العناوين تستخدم API نفسها، لكن قائمة المحافظات في نموذج الويب محدودة بخمس قيم، بينما Native يستخدم قائمة المحافظات المشتركة الكاملة.
- الويب يخفي إضافة عنوان عند الحد 10؛ Native يعتمد على رفض API بدل إظهار الحد مسبقاً.

### المصادقة والاسترجاع

- Native يجمع login/register/forgot في شاشة واحدة؛ الويب يفصل login/register/forgot/reset/verify.
- تسجيل دخول Native يستعمل Supabase مباشرة؛ الويب يمر عبر `/api/auth/login`، لذلك rate limiting/cookie semantics ليست متطابقة.
- التسجيل Native يمر عبر `/api/auth/register`.
- استرجاع Native يرسل callback إلى الويب؛ لا توجد شاشة Native لـ reset-password أو verify-email ولا معالجة deep link كاملة لإتمام العملية داخل التطبيق.

### FAQ والتواصل والقانون

- أسئلة FAQ الست وإجاباتها مطابقة بالعربية والإنجليزية؛ shell فقط مختلف.
- Contact يستخدم الإعدادات وPOST نفسها؛ الويب يعرض نجاح/خطأ inline، Native يستخدم Alerts. Native قد يملأ بيانات المستخدم تلقائياً.
- الخصوصية والشروط من المصدر المشترك `@eurostore/shared/legal`، لذا المحتوى النصي مطابق؛ التنقل والـ shell ليسا مطابقين.

### اللغات والاتجاه

- الويب اجتاز حالات العربية RTL والإنجليزية LTR في الأحجام الثلاثة بلا overflow أفقي في المسارات العامة المفحوصة.
- Native يحفظ التفضيل في `eurostore-mobile-preferences-v1` ويغير `direction` والنصوص؛ لا يستخدم `I18nManager` restart، لذلك يجب عدم اعتبار كل سلوك مكوّنات النظام مطابقاً تلقائياً على iOS وAndroid.
- التحويل الفعلي داخل APK من العربية إلى English نجح وغيّر ترتيب BottomNav ومحاذاة النص إلى LTR فوراً.
- صفحة verify-email على الويب أظهرت عنواناً إنجليزياً في جلسة عربية، وهي فجوة ترجمة فعلية.

### الوصول Accessibility

- فحص الويب سجّل حالة أو أكثر في 137/192 فحصاً قبل إضافة المجموعة، وأبرزها hydration warnings، icon-only controls بلا اسم، inputs بلا label، وأهداف لمس أصغر من 44px. الرقم هو عدد حالات متأثرة وليس عدد عيوب فريدة.
- جرد Native: 104 عناصر `Pressable/TouchableOpacity` مقابل 57 `accessibilityLabel` و57 `accessibilityRole` فقط، و20 `TextInput`.
- أكبر الملفات المرشحة للفجوات: profile (10 تفاعلات/label واحد)، order detail (7/1)، checkout (5/0)، login (4/0)، addresses (5/2)، exchange new (3/0)، orders/notifications (3/0 لكل منهما).
- توجد حالات labels مشتقة أو عناصر نصية مفهومة بصرياً، لذلك لا يُساوى الفرق العددي تلقائياً بـ47 عيباً، لكنه يمنع شهادة الوصول 1:1.
- فحص UIAutomator الفعلي لعينات onboarding/home/products وجد 0 عناصر clickable بلا اسم ضمن 2 و7 و19 عنصراً على التوالي؛ هذا يقلل شدة الجرد الساكن في الشاشات المفحوصة فقط ولا يغطي بقية الشاشات.

### الثيم والألوان

- Web وNative يستخدمان الخلفية الفاتحة `#FAF7EF/#FFFDF8` والذهبي كـ accent؛ لا يوجد Dark theme عام في الإصدار الحالي.
- توجد قيم hex كثيرة مباشرة داخل Native بدلاً من semantic tokens؛ هذا يسمح بانحرافات مستقبلية حتى لو بدا اللون متقارباً الآن.
- الظلال، الخطوط، radii، أحجام الأيقونات، شريط النظام وارتفاعات العناصر تختلف؛ الثيم متقارب وليس مطابقاً.

الاختبار الحي الناجح أثبت: public catalog، رفض cart المجهول، profile الموثق، إنشاء عنوان، كتابة وقراءة cart، فشل ShamCash الآمن 503، إنشاء COD، idempotency، إنقاص المخزون مرة واحدة، PDF invoice، cancel، حفظ الحالة، واستعادة المخزون، ثم تنظيف البيانات.

## فروقات حرجة مرتبة

### P0 — تمنع شهادة 1:1

1. Bottom navigation وHeader/Footer غير متطابقة عبر الصفحات الداخلية.
2. استرجاع/تأكيد الحساب لا يكتمل Native-to-Native.
3. اختيار متغير المنتج لا يضمن التوافق متعدد الخصائص مثل الويب.
4. الدفع يختلف في الكوبون والملاحظات وحفظ العنوان وpayload ومسار النجاح.
5. إنشاء وتفاصيل الاستبدال ناقصة مقارنة بالويب.
6. بحث AppTopBar وضغط العلامة لا ينقلان الاستعلام/الفلتر نفسه.
7. لا توجد أدلة pixel-perfect؛ القياس الفعلي يثبت العكس.
8. نشر الويب الإنتاجي أقدم من عقد API الذي يعتمد عليه APK؛ الرئيسية والتصنيفات والمجموعات تفشل حتى نشر الـ APIs الجديدة.
9. تمرير كتالوج Android على المحاكي سجل jank مرتفعاً: 80% في الجولة الباردة و66% بعد دفء الكاش؛ لا يجوز اعتماد عبارة "بدون lag" قبل تحسينه وإعادة القياس على جهاز فعلي.

### P1 — فروقات مهمة

- featured/sale filters، URL state، pagination.
- wishlist/similar/recently-viewed في صفحة المنتج.
- تفاصيل السلة والطلب والولاء والحساب.
- error/retry states في الإشعارات والضيف والاستبدال.
- قائمة المحافظات غير موحدة.
- فجوات accessibility وأهداف لمس الويب.

### P2 — اتساق وصيانة

- توحيد semantic tokens بدلاً من hex المباشر.
- توحيد inline errors مقابل Alerts.
- توحيد labels والـ empty-state CTAs والـ microcopy.
- إزالة hydration mismatch في الويب.

## الخلاصة الصريحة

الربط الحقيقي بقاعدة البيانات موجود وقوي، والبنية Native وليست صورة عن الويب. لكن التطابق الحالي هو **تقارب في الهوية والمحتوى الأساسي، وليس 1:1**. المطلوب للوصول إلى شهادة فعلية هو تنفيذ عناصر P0 ثم إعادة تصوير كل مسار Native والويب على الأجهزة نفسها، مع حالات guest/auth/data/error/loading/empty، وتشغيل diff بعتبة محددة واعتماد يدوي على Android وiOS.
